Glossário rápido

Digest
O “endereço exato” de uma imagem (sha256…). Dois digests iguais são a mesma imagem. A produção usa só digest.
Tag
Um apelido para uma imagem no GHCR. Pode mudar de lugar. Por isso não se faz deploy por tag.
Runner
Programa que fica ligado numa máquina e executa os jobs do GitHub Actions. Ele só conecta para fora.
Environment
Conjunto de segredos e variáveis do GitHub, lido só pelos jobs que o nomeiam e só nas branches permitidas.
Ruleset
O cadeado de uma branch: só entra por pull request, com checks verdes e, na main, com a sua aprovação.
Túnel e Access
O túnel leva o tráfego da Cloudflare até o Atlas. O Access exige login antes de qualquer página aparecer.
Migração
Mudança no formato do banco. Aqui só valem as aditivas. Uma destrutiva aborta o deploy.
Health check
Pergunta ao app “você está bem?”. Se não responder, o deploy volta para a imagem anterior.
Bot / App
Conta-robô da organização. Substitui tokens pessoais nos agentes.

Servidores e o que cada um faz

Quatro lugares importam: o seu computador, dois servidores seus e a nuvem (GitHub e Cloudflare).

Hermes seu computador

Para que serve

É de onde você manda. Abre o navegador, aprova pull requests e entra nos servidores por SSH.

O que tem
  • Terminal Ghostty e o comando lvgs -a --claude.
  • Seu login pessoal do GitHub e a sua chave SSH.
  • Nenhum segredo de produção.
Cuidados

Desligar o Hermes não derruba nada. O Claude roda dentro do tmux do Atlas e continua lá.

Atlas servidor de execução

Para que serve

Roda a aplicação e o banco. Executa os deploys. É onde os agentes trabalham.

O que tem
  • Debian 13, 8 CPUs, 7,5 GB de memória, Docker.
  • Containers de produção, o cloudflared e (parados) os da homolog.
  • O runner de deploy como serviço (github-deploy).
  • O tmux lvgs-claude com esta conversa.
  • Os comandos lvgs-browser, lvgs-access e lvgs-env-apply.
Quem acessa

Você por SSH como lucas. O robô age pelo git e gh do Atlas. O runner roda como github-deploy.

Oreon servidor de build

Para que serve

Testa, constrói a imagem e publica no GHCR. Código de pull request roda aqui, e não no Atlas.

O que tem
  • Runner oreon-ci com label oreon.
  • Podman sem privilégios (rootless), jq, curl, flock, Python.
  • Uma fila só: um job por vez.
Cuidados

Nunca recebe segredo de produção nem faz deploy. Se faltar uma ferramenta aqui, o CI quebra.

O caminho do código até a produção

Cada raia mostra quem faz o passo. Leia da esquerda para a direita.

  1. Pull request. O robô cria uma branch a partir da homolog, escreve o teste primeiro, abre o PR. Nenhum agente trabalha direto na main ou na homolog.
  2. CI no Oreon. Rodam três checks com nomes fixos: Python unit tests (Oreon), Frontend typecheck and build (Oreon) e Image build and smoke test (Oreon). Os jobs de publicar e fazer deploy aparecem como “skipped” no PR, e isso é o certo.
  3. Revisão e merge. Um reviewer novo lê o PR e termina com VERDICT: APPROVED <sha>. O robô só mergeia se o commit for exatamente esse e os checks estiverem verdes.
  4. Publish. The pinned reusable engine builds on homolog and publishes <sha>, approved-homolog-<sha>, homolog, and tree-<tree>.
  5. Deploy homolog. Opt-in with DEPLOY_HOMOLOG=true. It runs on the isolated Oreon VM. It is off for the pilot. The owner creates Access, route and DNS outside CI.
  6. PR de promoção. O robô abre o PR da homolog para a main com um resumo claro.
  7. Você aprova. É o único clique obrigatório. Escolha “Create a merge commit” para a árvore da main ficar idêntica à da homolog.
  8. Promotion. Main retags the tested manifest in GHCR as <sha> and approved-<sha>. No rebuild or image repush occurs. The digest stays identical.
  9. Production deploy. The reusable workflow runs migrations, replaces the app by digest and proves its digest and health revision. Cloudflare routing is an owner prerequisite. The external check accepts HTTP 200 or an Access login redirect.

Imagens, tags e digest

Projects keep a thin ci.yml, deploy/project.json, and deploy/env-manifest.json. They never copy the engine. Production calls pin the 40-hex commit SHA of a release tag. Optional manifest values use required:false; GitHub cannot store empty secrets. The orchestrator prepares the engine release PR with scripts/release.sh vX.Y.Z. The owner merges and runs lvgs-access scripts/release-finalize.sh vX.Y.Z [--dry-run] in the engine clone. The orchestrator then opens project pin PRs. Follow engine releases for the canonical procedure.

A imagem é construída uma vez na homolog. A produção recebe a mesma imagem, e não uma nova construída do mesmo código.

TagQuem enviaPara que serve
<sha>Homolog e mainIdentifica o commit.
tree-<árvore>HomologLiga a imagem ao conteúdo do código. A promoção usa esta.
homologHomologA imagem mais nova da homolog.
approved-homolog-<sha>Homolog (por último)Não casa com o padrão que o Atlas lê.
approved-<sha>Só a mainO padrão de produção. Um “guard” impede qualquer outra branch de enviar.
Regra de ouro: o deploy usa ghcr.io/lvgs-dev/server-supply@sha256:… (digest), e nunca uma tag. Uma tag pode apontar para outra imagem amanhã; um digest nunca muda.

Como o token do robô nasce

  1. Um script interno assina um pedido curto com a chave app.pem.
  2. O GitHub devolve um token de instalação que vale 1 hora, só com as permissões do App.
  3. O script guarda uma cópia por 45 minutos. Na vez seguinte ele devolve a cópia ou pede outro.
  4. O git pede a senha ao “credential helper” do github.com, que devolve o token. O gh usa o mesmo token por um atalho.
  5. Nada roda em segundo plano e nenhum cron renova token. Quem precisa, pede.

O que o App pode e não pode

pode

  • Enviar branches e abrir pull requests.
  • Mergear na homolog (com revisão e checks verdes).
  • Editar arquivos de workflow.
  • Ler o resultado do CI.

não pode

  • Mudar rulesets, Environments ou segredos.
  • Aprovar um PR que ele mesmo abriu.
  • Mergear na main.
  • Reexecutar jobs (Actions é só leitura).
Tokens antigos que você apagou ou vai apagar: GH_TOKEN, atlas-dev, atlas-build-lvgs-ui, server-supply-lvgs-ui-read, o do GitHub Models, Atlas GHCR Read Only, atlas e o segredo LVGS_UI_READ_TOKEN. Eu só consigo conferir o segredo de repositório; os tokens pessoais só aparecem na sua tela do GitHub.

Environments: de onde vêm as configurações

Nenhuma configuração é editada no servidor. O job de deploy lê o Environment, escreve os arquivos e sobe o container. Para mudar um valor, edite o Environment e rode o job de novo.

homolog

  • Só aceita deploy da branch homolog.
  • Sem revisor obrigatório.
  • Banco, senha, porta e pasta próprios.

production

  • Só aceita deploy da branch main.
  • Sem revisor obrigatório: a aprovação é no PR.
  • Porta, projeto e alias fixos no próprio job.

Interruptores (variáveis do repositório)

VariávelO que controlaPadrãoComo mudar
DEPLOY_HOMOLOGO job Deploy homolog (VM). O publish não depende dela.server-supply: desligado (só roda com o valor true). Projeto novo: ligado (roda, a menos que seja false).Veja a aba Comandos.
Desligar não para os containers, e ligar não faz deploy sozinho: depois de ligar, dê um push na homolog. A variável é do repositório (e não do Environment) porque a condição do job é lida antes de o Environment ser escolhido. Só você muda: o robô não tem essa permissão.
Duas regras para os valores: nunca use aspas simples (') em um valor, e não crie segredo vazio (o GitHub recusa). Deixe-o sem criar e o job recebe vazio.

Redes, nomes e o defeito que tivemos

Dentro do Docker, cada container responde por nomes. O Compose acrescenta o nome do serviço como apelido em toda rede onde o container entra. Foi isso que misturou a produção com a homolog.

RedeQuem está nelaPara quê
server-supply_internalApp e banco da produçãoRede do projeto de produção. O banco só existe aqui. O cloudflared não entra nela.
server-supply-homolog_internalApp e banco da homologRede do projeto de homolog. Não é compartilhada.
edgecloudflared e o app da homolog (se ligado)Compartilhada. Só o app entra aqui, nunca o banco.
bridgecloudflaredPadrão do Docker.
Regra: nunca rotear por nome de serviço quando o cloudflared enxerga mais de uma rede de projeto. Use o nome do container, que é único, e descubra-o por rótulos do Compose.
